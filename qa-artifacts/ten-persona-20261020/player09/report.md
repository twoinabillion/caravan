# player09 — 약속을 끝까지 지키는 성실한 배달부

최종 새 실행 attempt02에서 세 마을 무전 3/3과 보유 부품 조달을 모두 실제 납품한 뒤 본편 엔딩까지 갔다. DAY 8, 895km, 61번 선택, `story_done=true`, `ending=story_done`, `method=core_transfer`다. 생산 파일·공용 어댑터·다른 플레이어 기록·실제 사용자 저장은 변경하지 않았다.

이것은 실제 소스 엔진을 Node VM과 격리 메모리 저장소에서 실행한 자동 감사다. 사람·브라우저·시각·음성·UI 취소 검수가 아니다.

## 먼저 정한 기준과 두 실행

`policy.cjs`에 선택 전에 성향과 기준을 선언했다. 맡은 짐과 기록을 끝까지 운송하고, 전달한 장소의 게시판에서 후속을 확인한다. 세 마을 무전 3단계와 소지품 조달을 마친 뒤 부모님의 흔적과 남산으로 간다. 공개 본문·선택 label/hint·비용·목표·경로 예측·보유량만 사용하며 결과/fx/숨은 플래그는 선택에 쓰지 않는다. seed는 201009, 시작 짐은 provisions, `reloadAfterChoice=true`다. 동승은 따로 모집하지 않았고 전 과정 혼자였다.

| 실행 | 엔딩 | 선택 / trace | 실제 완료와 한계 |
| --- | --- | --- | --- |
| attempt01 | DAY 7 / 916km / story_done / core_transfer | 63 / 265 | 무전 3/3, 약장 1/3 납품. 보유 부품 조달은 정책 우선순위 때문에 지나침 |
| attempt02 | DAY 8 / 895km / story_done / core_transfer | 61 / 267 | 무전 3/3 + 부품 2개 조달. 대기 후속 없이 본편 완료 |

첫 원본과 정책을 보존했다. 첫 실행의 대전 게시판에는 부품 4개를 가진 상태에서 부품 2개 조달이 공개돼 있었다. 두 번째 정책은 그 조달을 먼저 끝내고 같은 게시판의 무전 후속을 다시 맡는다. 미래 결과나 목적지를 하드코딩하지 않았고 자원·플래그·동료를 주입하지 않았다. 두 실행의 n1–79는 JSON 전체가 동일하다. 최종 목적을 채운 뒤 세 번째 실행이나 불필요한 정책 개선은 하지 않았다.

## 끝까지 운송한 기록

최종 실행에서 무전 의뢰를 밀양→대전→광주→밀양으로 이어 갔다. 2/3은 본편의 짧은 북상길에서 크게 벗어나는 광주 운송이었지만, 맡은 이상 경로를 바꾸어 끝까지 갔다. 긴 우회 때문에 본편은 이미 540km를 달려 밀양으로 돌아온 뒤에도 계속 남아 있었다. 누적 거리를 서울 도착으로 혼동하지 않고 현지 탐색 안내를 따라 청주·천안·평택·수원에서 근거를 보완한 뒤 실제 서울 관문을 통과했다.

최종 저장은 `storyQuests.completed=["relay"]`, `active=null`, `questFollowup=null`이다. 완료 장부도 네 건 모두 실제 총 지급량 20/18/26/28을 기록한다. 기한 없는 연속의뢰를 101~103일차라는 내부 due 수치만 보고 기한 압박으로 해석하지 않았다. 이 실행에서는 만료가 없었고 늦은 납품도 시험하지 않았다.

첫 실행은 무전 3/3 뒤 밀양의 약장 1/3을 추가로 맡아 수원에서 실제 납품했다(n139→206, 고철 +22). 남은 약장 2/3은 아직 수락하지 않은 후속 제안이다. `storyQuests.active`가 그 후속을 보관하지만 강제로 이미 수락했다고 해석하지 않는다. 최종 실행에서는 조달을 합쳐 네 건의 목표가 충족돼 새 연속의뢰를 맡지 않았다.

## 보급·재접속·다음 행동

연료는 공개 거래로 사고 현장의 가능한 행동을 돌아가며 수행했다. 밀양 국수 좌판은 고철을 쓰는 행동이었다. 모든 `status.ok`를 열어 둔 정책이 이를 돈벌이로 오인했지만, 다음 부품 천막 노동에서 실제 부품과 고철을 벌었으므로 이 선택을 게임 오류로 세지 않는다. 무주의 촛불 순찰과 환기팬, 대전의 물 배급 화이트보드도 실제 수행했다. 노동을 정규식 라벨로 버리지 않았고, 보급은 실제 시간·피로·고철 비용을 냈다.

두 실행 모두 공개 경로 예측의 `shortage=true`인 출발은 0회였고 연료 고갈 구제·사망·무한 노동·실행 한도는 없었다. 현재 자원과 다음 구간 연료 예측을 보급 목표에 반영했다. 저장 관측에 보관 상한 수치가 직접 없어서 실패한 구매는 관측된 이전/이후 수량으로 차단하는 정책이지만, 이번에는 한도 때문에 실패한 거래를 실제로 밟지 않았다. 좌석이 필요한 동승 요청이나 업그레이드도 밟지 않았다.

각 서사 선택 뒤 지급 재접속은 총 124회(63+61), 수락/납품 직후 별도 저장로드는 16회(각 8)였다. 전부 성공했고, 지급 재접속은 `replayed=true`, `applied=false`, 전후 관측이 같았다. 수락/납품의 아이템·고철·완료 상태도 다음 재접속과 최종 장부에서 유지됐다. 이 검사는 버튼을 다시 눌러 같은 지급이 막히는 엔진 검사이며 실제 브라우저 복원이나 포기/뒤로 입력을 대신하지 않는다.

최종 자원은 연료 36.868L, 물 20, 식량 10, 고철 86, 차체 87.08%, 부품 6이다. 두 실행의 서사 결과에 나온 연료·물·식량·고철·차체 chip 20개는 실제 변화와 맞았다. 기본 보상 알림과 빠른 처리 보너스가 따로 나온 것은 합계로 대조했다. 기존에 고친 완료 장부 보너스 누락을 새 오류로 반복하지 않는다.

## 발견과 해석

`findings.json`에는 제품 버그 후보 1건, 기존 의견 계열 1건, 정책 오류 1건을 분리했다.

- P09-B01: 야영 직후 피로 0에서 트럭 카페 커피를 사면 피로는 0→0인데 결과 chip이 `피로 -5`라고 한다(attempt01 n126, attempt02 n131). `src/04d-engine-director.js:452–453`이 피로를 clamp한 뒤 요청값으로 chip을 만드는 것을 확인했다. `src/07-ui.js:4552–4562`의 결과 renderer도 피로 chip을 `story-changes` 목록으로 출력한다. 다른 자원의 실제 델타 수선은 정상이다. 이는 실제 결과 표시 경로에 연결된 영수증 값 문제이며 시각 배치 문제를 확정한 것이 아니다.
- P09-O01: 첫 실행에서 우편부 편지를 실제로 맡고 한강에서 끝까지 전달하겠다고 말했지만 본편 엔딩에는 수신인에게 건네는 장면이 없고 편지는 남아 있다. 기존 `M03-postman-open-request`의 거절 경로 의견과 같은 계열에 수락 경로의 증거를 보탠다. 다음 세션에 남긴 약속일 수 있어 새 기능 버그로 집계하지 않는다.
- P09-H01: 첫 정책의 조달 우선순위 누락과 generic 1/3 가산은 감사 정책의 문제다. 첫 실행을 지우거나 성공 경로로 덮지 않고 새 실행으로 보완했다.

대전에서 조달 완료 직후 같은 제목의 조달이 다시 게시된 것은 관측했다(n84). 다시 수락하지 않았으므로 중복 보상이나 무한 지급을 입증하지 않았다. 같은 날 게시판 재사용 규칙과 재의뢰 가능성도 있어 확정 후보로 올리지 않는다. 서울 진입 본문의 일반적인 편지·봉투는 본편 서류를 가리킬 수 있으므로 소지품 객체만 보고 유령 아이템 버그로 세지 않는다. 종장의 밤·새벽·수원 귀환은 이미 후일담 시간 마커가 있는 구간이므로 고정 엔진 시각만으로 무료 시간 이동 오류를 재제보하지 않는다.

## 전체를 읽은 감상과 범위

배달부 성향에서는 첫 장부를 넘겼을 때 새 주파수표가 나오는 흐름, 다시 남쪽으로 가서 교대 장부를 돌려주는 흐름이 가장 분명했다. 작은 화물 운송이 떨어진 마을의 같은 주파수로 이어졌고, 본편에서 증언 사본과 원본을 다른 길로 나누는 선택에도 같은 태도를 가져갈 수 있었다. 즉시 가능한 조달을 사이에 처리해도 무전 후속이 사라지지 않은 점과 재접속 뒤 완료 장부가 맞은 점은 신뢰할 만했다.

긴 우회는 DAY와 누적 km를 늘렸지만, 이 한 성향의 연료 잔량이나 엔딩 비율을 전체 밸런스의 근거로 삼을 수 없다. 자동 점수 정책이 돈을 벌려다 국수를 사거나 위험 hint가 없는 다른 입구에서 다치는 선택도 했다. 이는 현실의 성실한 배달부가 반드시 하는 행동이라는 주장이 아니다. 첫 실행의 남산 편지는 이 성향에서 특히 마음에 남는 열린 약속이었다.

attempt01 n1–265를 전부 읽었다. attempt02 n1–79는 원본과 JSON 완전 동일함을 대조하고 n80–267의 모든 action·진입·선택·결과·시간·자원·알림을 읽었다. `audit-evidence.json`은 전후 수치와 완료 장부, 재접속 검증, 공개 연료 부족 예측 유무를 다시 계산한 자료다. 마지막 엔딩 증거는 attempt02 n266 결과의 `SESSION 1 END`, n267 중복 지급 없는 재접속과 summary/save의 본편 완료다. 두 실행 source hash는 `6f9b628b020bcc8b22034294185f9b8dcf0ec4bdaa3f6efa4f5689b1196161b4`로 같다.

미검증: 실제 Studio·브라우저·레이아웃·그림 crop·페이지 나눔·음성·키보드·터치·사람의 이해, 실제 사용자 저장, 의뢰 포기/취소/만료/기한 경계/늦은 납품, 반복 조달 재수락, 약장 2/3·3/3, 모든 다른 서사 선택과 최종 집행안. 공용 어댑터에 의뢰 포기 action이 없으므로 상태 조작으로 대신하지 않았다. 새 서버나 탭을 열지 않았다.

증거 파일은 `policy.cjs`, `retry-policy.cjs`, 두 `attemptNN/` 원본 trace/summary/save/coverage, `read-trace.cjs`, `verify.cjs`, `audit-evidence.json`, `findings.json`이다.
