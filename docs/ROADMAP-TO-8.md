# 파트 1. 공정 — 먼저 이걸 고쳐야 나머지가 지켜진다

## 원칙 1. 게이트는 자기가 지킨다는 걸 증명해야 한다

8/6 사이클의 검사 넷은 **자기가 이름 붙인 기능을 되돌려도 초록**이었다.
앞으로 새 검사를 추가할 때는 반드시 다음을 통과시킨다.

**뮤테이션 확인(Definition of Done의 일부)**
```
1. 검사를 작성한다 → 초록 확인
2. 그 기능을 코드에서 되돌린다(한 줄 주석 처리로 충분)
3. 검사가 빨간불이 되는지 확인 ← 안 되면 그 검사는 아직 검사가 아니다
4. 되돌린 것을 복구하고, 2~3에서 본 것을 검사 파일 주석에 남긴다
```

이번에 넣은 `tests/test_choice_visibility.py`, 야영 판정, 결정성 비교면 자체 검사가
이 형식의 예시다. 특히 **"비교면이 비어 있지 않은가"를 검사 안에서 확인**하는 패턴
(`out:` / `dawn:` 항목 수 확인)은 다른 검사에도 이식할 것.

## 원칙 2. 주장에는 재현 명령을 붙인다

결과 문서에 쓰는 모든 수치 옆에 **어떻게 다시 재나**를 적는다. 8/6 초판 문서의
"백미러 73→64"는 작업 중간값을 베이스라인으로 착각한 오기였고, 재현 명령이 있었으면
쓰는 순간 걸렸다.

```
❌ "목발 단어를 크게 줄였다"
✅ "한참 83→43 (git show <before>:src/03-data.js | grep -o 한참 | wc -l)"
```

실측(이미 일어난 것)과 전망(그럴 것)은 문장에서 분리한다.

## 원칙 3. 릴리스 전 적대적 재검증을 정식 단계로 둔다

이번에 효과가 증명된 절차다. 구현자가 아닌 리뷰어에게 **결과 문서를 "미검증 마케팅"으로
취급하고 코드로 대조**하게 시켰더니, 살아 있던 XSS·거짓 통과 게이트 4종·내가 만든 UI
회귀가 한 번에 나왔다. 자기 채점으로는 절대 안 나왔을 것들이다.

절차: 구현 → 자체 게이트 통과 → **적대적 재검증** → 반박 수정 → 게이트 재통과 → 커밋.
반박당한 주장은 문서에 표로 남긴다(지운다고 없던 일이 되지 않는다).

## 원칙 4. "배선됐다"와 "발동한다"를 구분해서 센다

DAY 30은 코드에 배선됐지만 실완주가 3~4일이라 날짜 축은 영영 안 닿았다.
새 시스템에는 반드시 **실엔진 시뮬에서 발동률**을 붙인다.

```
배선 확인:  단위 검사 (함수를 직접 호출)
발동 확인:  실엔진 시뮬에서 이 기능이 관여한 런의 비율
```
발동률이 낮으면 기능이 아니라 죽은 코드다. 신규 이벤트도 같은 기준으로 본다
(현재 갈등 아크 3.3% · 가짜 행정소 2.6% · 회수조 3.0% — 사실상 아무도 못 본다).

## 원칙 5. 한 사이클에 한 축만 건드린다

8/6에는 7개 Phase를 한 커밋에 넣어 무엇이 무엇을 깼는지 분리가 안 됐다
(전투 UI 회귀가 게이트를 통과해 버린 것도 이 때문). 앞으로는 웨이브당 한 축,
웨이브마다 게이트 통과 + 시뮬 리포트 갱신 + 커밋.

## W1 — 시간에 값을 매긴다 (키스톤)

**문제**: 시한 30일, 실완주 중앙 DAY 3~4. 배급·의뢰 기한·시한·피로가 전부 공짜라
"연료냐 왕진이냐" 같은 갈등이 도덕적 산수가 아니라 취향 선택이 된다.

**두 가지 방법이 있고, 하나를 고른다.**

| | A. 시한을 압축 | B. 하루를 비싸게 |
|---|---|---|
| 방식 | `D.transferDeadlineDay` 30 → **7** | 주행·사건·정비가 시간을 더 먹게 |
| 장점 | 데이터 한 줄, 즉시 검증 가능 | 서사(30일) 유지 |
| 단점 | 인트로·노트의 "30일" 문구 수정 필요 | 파급이 넓고 튜닝이 오래 걸림 |
| 권장 | **A로 먼저 실측**하고, 여유가 없으면 B로 미세조정 | |

**A안 작업 목록**
1. `D.transferDeadlineDay` = 7, 인트로·노트·`transferStatus` 문구 동기화
2. 압박 단계를 날짜 축으로 되돌린다(거리 축은 보조로만) — 지금은 거리 축이 무조건
   발동해 `deadlineSeenPct 100%`가 동어반복이다
3. 정착지 체류·탐색·수리가 반나절 이상을 먹도록 재조정 → 하루가 실제 선택이 되게
4. 초과 시 첫 이송이 **실제로 좌석을 가져간다** — 늦은 날수만큼 구제 불가 인원을
   `seoul_costs`·에필로그에 수치로 새긴다

**8점 방어 조건 (전부 실엔진 시뮬로 측정)**
- 정책 간 소요일 스프레드 **≥ 2일**
- **가장 느린** 정책의 시한 초과율 **≥ 30%**, **가장 빠른** 정책은 **≤ 20%**
- 완주 런의 중앙 DAY가 시한의 **35% 이상**, 가장 느린 정책은 **70% 이상**
- 시한 초과 런과 준수 런의 엔딩 텍스트가 실제로 갈라진다(스냅샷 검사)

> ⚠️ 초판 정정: 처음에는 "`direct`의 시한 초과율 ≥30%"라고 썼는데, 실측해 보니
> `direct`가 **가장 빠른** 정책이었다(모델이 거꾸로였다). 실제 긴장의 축은
> "서두름 vs 철저함"이므로 기준을 최속/최저속 기준으로 바로잡았다.
> 또 하나 발견: 초판 지표가 **미완주 런(timeout)까지 "시한 초과"로 집계**하고 있었다.
> "늦게 도착했다"와 "도착 못 했다"는 다른 상태라 완주 런 기준으로 분리했다.

**영향**: 코어 루프 6→7.5, 스토리 7→7.5 (기존 이벤트가 재평가됨)

### W1 실행 결과 (2026-08-06) — 적대적 재검증 반영본

> 초판을 그대로 두지 않고 다시 썼다. 독립 리뷰어가 **치명 2건**을 포함해 16건을 반박했고,
> 그중 초판의 헤드라인 숫자 자체가 무효라는 지적이 맞았다. 아래는 수정 후 상태다.

**무효화된 것 — 측정 대상을 잘못 알고 있었다**

시뮬의 "완주"는 서울 노드에 닿는 순간을 셌는데, 그 시점의 네 기둥은 0/4·0/3·0/4·0/2였다.
실엔진은 그 상태에서 **관문이 수원으로 되돌려보낸다**(`04-engine.js:2495`). 즉 초판이
"완주 소요일"이라 부른 값은 *빈 장부로 서울 땅을 처음 밟는 날*이었다.
자동 플레이어는 동료 아크·서사 수집을 수행하지 못해 과업(deeds)이 **0건**에 머문다 —
영입 로직을 붙여 봐도 party는 0이었다. **이 도구로는 완주 시간을 잴 수 없다.**

지표 이름을 `daysToSeoulNode`로 바꾸고, 게이트 조건도 잴 수 있는 것만 남겼다.

**시한 값의 근거 — 추정이 아니라 계산**

완주 시간을 못 재므로, 대신 **완주에 필요한 순회 거리**를 계산했다.

| | 거리 |
|---|---|
| 직행 경로 (부산→서울) | **356km** |
| 완주 필수 23개 지점 순회 (정착지 전부 + 영입 목표 + 서울) | **1,430km** (4.0배) |

시뮬 실측 일당 진행이 71km/일(직행 356km ÷ 중앙 5일)이므로 완주형은 **약 20일**.
`D.transferDeadlineDay = 20`으로 확정했다.
⚠️ 이 값은 *완주 소요일 실측*이 아니라 *필수 순회 거리 기반 산출*이다.
**사람 플레이 1회로 검증해야 한다** — 현재 최상위 미해결 항목.

**실측 (`npm run simulate:engine` = 60런, 정책당 20런, seed 400000001)**

| | 개편 전 | 개편 후 |
|---|---|---|
| 시한 | 30일 (선언만, 닿을 수 없음) | **20일** (순회 거리 앵커) |
| 서울 노드 도달 중앙 DAY | 3~4 | **직행 5 · 준비 6 · 탐색 9** (시한의 25~45%) |
| 정책 간 스프레드 | 1일 | **4일** |
| 런당 사건 수 | 21~25건 | **23 / 39 / 53건** |
| 지각의 대가 | 텍스트 문구 | **하루 = 버스 12대 · 540명** (코어·에필로그에 수치로) |

**실제로 바꾼 것 (검증됨)**
- 평균 시속 44→13km/h + TIMESCALE 2.2→7.4. 초당 진행 거리 1.613 → 1.603km(−0.6%)라
  실시간 체감은 거의 같고 게임 내 하루만 무거워진다.
  ⚠️ 단, **피로·배급·날씨는 게임 분 기준이라 실시간으로는 3.4배 빨리 온다** —
  같은 거리를 달릴 때 피로가 3.4배 쌓인다는 뜻이다. 의도한 난이도 상승이지만 초판은 이를 밝히지 않았다.
- 정비 3~5시간 · 수리 2~3시간 · 거래 25~40분이 시간을 소비한다.
  **지불 전에 UI에 표시된다**(초판은 숨어 있었다 — 보이지 않는 비용은 선택이 아니다).
- 지각 하루 = 버스 12대·540명. 6,412명에서 정확히 상한 처리되며,
  **구역이 비면 별도 분기**로 갈라진다("멈출 것이 남아 있지 않았다").
- 시한 변경에 **세이브 마이그레이션**(v3) — 옛 30일 계약으로 달리던 세이브를 소급 청구하지 않는다.
- 압박 단계는 **날짜로만** 고른다(본문이 절대 날짜를 말하므로). 거리 축은 한 단계도 못 본 채
  코앞까지 간 경우의 안전망으로만 남겼다.

**초판이 만든 회귀 (수정 완료)**
- `routeForecast`·`travelForecast`가 44km/h를 하드코딩한 채 남아 **모든 주행 예상 시간이
  실제의 1/3.4**로 표시됐다(장터 219km → "4시간 59분", 실제 16시간 51분). 출발 버튼과 도착
  정산이 한 구간 안에서 모순됐다. `G.driveMinutes()` 단일 소스로 통일하고
  **`test:eta`를 신설**(뮤테이션 확인: 되돌리면 3.32배 불일치를 잡는다).
- `G.advance`가 트랜잭션 중 갈증 종료를 부를 수 있는데 호출자들이 확인하지 않았다 → 전부 가드.
- "서른 밤" 3건 등 시한 문구 잔존 → 코드·테스트·정본 문서에서 전부 제거.

**함께 잡은 잠복 결함**
- `dialogue-lint.cjs`가 `errors`를 선언 전에 사용 — 검사가 실패하는 순간에만 크래시하던 형태.
- 테스트 4곳이 시한·속도 상수를 복제 → 데이터/엔진에서 파생하도록 수정.
- 주행 tick 실수 누적으로 기상 시각이 389.9999.
- `lateTransferPct`가 미완주 런까지 지각으로 집계.

**미해결로 남긴 것**
1. **사람 플레이 1회** — 시한 20일의 유일한 검증 수단. (최우선)
2. 자동 플레이어의 서사 수행 능력 — 없으면 완주 관련 조건은 영원히 측정 불가(W4 선결).
3. `07b-ui-panel.js`의 정비 "약 1.5시간" 표기 vs `G.fieldRepair` 100분 — 기존 불일치.

## W2 — 쓴 것이 보이게 한다 (콘텐츠 전달)

**문제**: 894 이벤트 / 풀 가중치 5,918 / 런당 사건 ~22건. 이번에 쓴 콘텐츠는

1. **비트 승격**: 갈등 아크는 `w` 기반 랜덤이 아니라 조건 충족 시 큐에 넣는
   고정 비트로(딜리버리 이벤트·시한 이벤트가 쓰는 `queueStory`/`fixed` 방식)
   - 설계 확정: `D.journeyBeats`(거리 문턱 → `G.scheduleJourneyBeat` → `queueStory`)가
     이미 정확히 이 메커니즘이다. 다만 현재 구조는 거리 조건만 받으므로,
     **동료·플래그 조건을 받는 `when` 필드를 추가**해 갈등 아크(강우+박 선생 동승)와
     악의 조우(지역·구간)를 같은 레일에 올린다. 새 시스템이 아니라 기존 레일의 확장.
2. **등장률 계측을 게이트에**: 주요 서사 비트 목록을 정의하고, 실엔진 시뮬에서
   각 비트의 발동률을 리포트 → 목표 미달 시 실패
3. **풀 위생**: 802개 풀 이벤트 중 오래된 저가치 이벤트의 `w`를 낮춰 신규·맥락
   이벤트가 뜨게 (지금은 신규가 노이즈에 묻힌다)
4. **악의 조우 3~4개 추가** — 2개로는 "대비"가 통계적으로 안 만들어진다

**8점 방어 조건**
- 지정한 핵심 비트 각각의 런당 발동률 **≥ 60%** (또는 명시적으로 "희귀" 태그)
- 한 런에서 만나는 서로 다른 이벤트 종류 수의 중앙값이 현재 대비 **개선**
- 악의 계열 조우를 한 번 이상 만나는 런 **≥ 70%**

**영향**: 스토리 7→8, 캐릭터 8 유지(이미 좋은 것이 보이게 됨)

### ✅ W2 실행 결과 (2026-08-06)

**착수 전 실측이 추정보다 나빴다.** 방어 조건을 먼저 빨간불로 걸어 재 보니
등장률이 계산했던 3%가 아니라 **0%**였다. 원인이 두 겹이었다.

1. 무작위 풀(802 이벤트·총가중치 5,918)에 묻힌 것 — 예상대로.
2. **시뮬이 도착 후 예약 이벤트를 아예 못 보고 있었다.** 실엔진은 위치 이벤트·위기·
   예약 스토리를 `setTimeout`으로 여는데 동기 루프에서는 타이머가 돌지 않아
   여정 비트 층이 통째로 측정에서 빠져 있었다(W1 재검증에서 지적된 것과 같은 부류).

| | 개편 전 | 개편 후 |
|---|---|---|
| 악의 계열 조우율 | **0%** | **100%** |
| 악의 조우 종수 | 2 | **5** |
| 여정 비트 | 6 (본편만) | **12** (본편 6 + 세계 6) |

**바꾼 것**
- `D.journeyBeats`에 `when`(동료·지역·플래그·부상)과 `kind`(story/world) 추가.
  조건이 맞아야 성립하는 장면을 풀에 두면 등장률이 0에 수렴한다.
- 예약 방식: 도착당 1개만 예약하던 것을 **"조건 넘긴 것 전부 예약, 꺼내는 건 하나씩"**으로.
  전자는 앞선 비트가 자리를 차지해 뒤쪽 비트가 짧은 여정에서 영영 못 나왔다.
- 악의 조우 3종 신규: `salvage_claim`(자기들끼리 법을 만들고 집행하는 고물 수거단),
  `water_toll`(자물쇠 걸린 공동 우물), `signal_bait`(억양이 변하지 않는 구조 요청 —
  은수로 역추적하면 "원본은 진짜였을 것"이 드러난다).

**검증**
- 뮤테이션 확인 통과: 승격을 되돌리면 100% → **16.7%**로 떨어지고 게이트가 잡는다.
- 동료 조건 비트는 자동 플레이어가 동료를 못 얻어 구조적으로 측정 불가 →
  시뮬 대신 **단위 검사**(`test:beats`)로 이관. 조건 미충족 시 안 열리고, 두 동료가
  타면 열리고, **다치면 다시 닫히는 것**까지 확인한다.
- 비트 정의 위생 검사(실재 이벤트 참조·거리 정렬·중복)도 추가했고, 넣자마자
  내 정렬 실수를 잡았다.

**미해결**
- 풀 위생(오래된 저가치 이벤트의 `w` 하향)은 손대지 않았다. 승격만으로 목표를
  넘겨서 지금은 불필요하고, 건드리면 기존 밸런스를 흔든다.
- 한 런에서 만나는 이벤트 종류 수 개선은 별도 측정이 필요하다(현재 미측정).

## W3 — 전투를 결정으로 (깊이)

**문제**: 48개 전투 선택 중 **21개(44%)가 판정 없는 확정 결과**. 교전은 5종뿐이고,
모든 조우에 값싼 이탈구가 있다.

**작업 목록**
1. phase 1과 현장 임무 phase 2의 확정 선택에 판정을 부여하거나, 판정이 없다면
   **전망 표시를 떼고 "준비 행동"으로 명시** (지금은 확정 결과에 등급이 붙어 혼란)
2. **이탈에 값 매기기**: 지금은 연료 4·차체 3이면 어떤 교전이든 회피 가능.
   이탈은 관측 상승·동료 신뢰·해당 서사 훅 상실 중 하나를 지불하게
3. **관측(pursuit)에 임계 효과**: 현재 임계 분기가 사실상 없다(가중치 조정과
   몇몇 지역 이벤트 게이트뿐). 3에서 강제 검문, 5에서 정착지 거부/기둥 봉쇄
4. 교전 2종 추가(북부 외 지역에도) — 5종은 15단계라도 반복이 빨리 온다

**8점 방어 조건**

- 이탈 선택률이 정책 무관 **≤ 40%** (지금은 사실상 최적해)
- pursuit 3·5에서 실제로 다른 사건이 발생함을 시뮬로 확인
- 전투 결과 분포가 성공/부분/실패 **세 갈래 모두 10% 이상**

## W4 — 경제가 물리게 (성장)

## W5 — 최종막을 결정으로

**문제**: `seoul_costs`는 선택지가 **1개**인 페이지 넘김이고, 세 처분에는 요구 조건·
실패·자원 비용이 없다. 대가 극화는 됐지만 "저항"은 과장이었다.

**작업 목록**
1. 세 처분에 **요구 조건**을 건다 — 인계는 실제로 이은 거점 수, 보존은 야간 근무를

3. `seoul_costs`를 실제 선택으로 — 무엇을 먼저 확인할지 고르고, 고른 것만 알게 된다
4. 동료 반대를 누르면 **비용을 지불**한다(유대 하락·에필로그 기여 상실)

**8점 방어 조건**
- 준비 상태에 따라 잠기는 처분이 실제로 발생(시뮬 확인)
- 엔딩 종류 **≥ 5** (처분 3 × 시한 준수/초과 + 패배)
- 반대 무시가 에필로그 텍스트를 바꾸는 것을 스냅샷 검사로 고정

**영향**: 스토리 8→8.5, 캐릭터 8 유지

# 파트 3. 웨이브 운영 방식

각 웨이브는 동일한 5단계를 밟는다.

```
1. 착수 전  — 그 웨이브의 방어 조건을 먼저 게이트에 넣는다 (빨간불로 시작)
2. 구현     — 한 축만
3. 자체 검증 — 게이트 초록 + 실엔진 시뮬 리포트 갱신
4. 적대적 재검증 — 다른 리뷰어에게 "미검증 마케팅" 취급으로 코드 대조
5. 반박 수정 → 게이트 재통과 → 커밋 (반박 내역은 문서에 표로 남김)
```

**1번이 핵심이다.** 방어 조건을 먼저 빨간불로 만들어 두면, 구현이 끝났는지를
사람이 판단하지 않는다. 8/6에는 이걸 나중에 붙여서 "통과하도록 쓴" 검사가 됐다.

## 진행 관리

- 웨이브마다 `reports/engine-simulation.json` 스냅샷을 남겨 추세를 본다
- 점수는 웨이브 종료 때마다 **적대적 재채점**으로만 갱신한다(자기 채점 금지)
- 미해결로 남긴 것은 문서에 남긴다 — "안 했다"와 "못 봤다"는 다르다

|---|---|---|---|
